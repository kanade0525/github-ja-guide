# 用語辞書の育て方

辞書は `src/glossary.js` の 1 ファイルです。2026-09-29 時点で **208 語**。

## 書き方

```js
'Squash and merge': {
  ja: 'まとめて取り込む',
  desc: '細かい変更記録を 1 つにまとめてから本体に合流させます。履歴がすっきりします。',
},
```

| 項目 | ルール | テストで縛っているもの |
|---|---|---|
| キー | GitHub の画面に出るとおりの綴り。単数形・複数形は別々に登録 | 前後の空白・連続空白なし、大文字小文字を無視した重複なし、**ソース上の重複なし** |
| `ja` | 横に添える短い言い換え | 12 文字以内 |
| `desc` | ホバーで出る説明。専門用語を使わず 1〜2 文 | 11 文字以上、`ja` と同じ文字列でないこと |

`npm test` で検査されます。

> JS のオブジェクトリテラルは同じキーを 2 回書いても**エラーにならず後勝ち**になります。
> 先に書いた訳が黙って消えるため、ソースの字面で重複を検出するテストを入れてあります。

## 足す語を見つける

実際の GitHub を巡回して、**まだ辞書にない UI ラベル**を集める方法を使いました。

1. 拡張を読み込んだブラウザで 15 種類のページを開く
2. 注釈対象になりうる領域（本文・コード・入力欄を除いた場所）のテキストノードを集める
3. 辞書にないものを、出現したページ数の多い順に並べる

この方法で分かったこと:

- **未ログインだと、上位はすべて GitHub のマーケティング用メガメニュー**（Platform / Solutions / Enterprise など）になる。
  実際の利用者はログインしているので、これらは優先度が低い
- 実務で効くのは、**個別のページにだけ出るラベル**（`Expand Up`、`View workflow file`、`Review required` など）
- 人名・リポジトリ名・言語名（TypeScript など）が混ざるので、そのまま採用してはいけない

## 足してはいけないもの

| 種類 | 理由 |
|---|---|
| 人名・アカウント名 | 固有名詞。誤って注釈が付くと失礼になる |
| リポジトリ名・ファイル名 | プロジェクトごとに違う |
| プログラミング言語名 | 訳す意味がない |
| 文章の途中に出る語（`opened`、`commented` など） | 一覧に何百個も並び、画面が読めなくなる |
| 数字や記号を含む短い断片 | 誤爆のもと |

## 誤爆を見つけたとき

1. まず `src/match.js` の `EXCLUDE_SELECTOR` に、その領域を足せないか考える（こちらが本筋）
2. 領域で切れない場合だけ、辞書からその語を外す
3. `tests/fixtures/github-mock.html` に再現する DOM を足し、E2E に回帰テストを書く

実際にこの手順で直した例:

- 検索欄の `is:pr state:open` の `open` に「未解決」が付いた
  → GitHub の検索欄は `<input>` ではなく `role="combobox"` のウィジェットだった
  → `[role="search"]` `[role="combobox"]` `[role="searchbox"]` `[role="textbox"]` `.QueryBuilder` を除外に追加
